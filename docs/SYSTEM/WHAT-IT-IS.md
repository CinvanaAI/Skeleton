# Skeleton System: What It Is

## Scope

- `kind`: whole-platform architecture
- `semantic owner`: no single sovereign owner; the platform is governed by the 7 Ownerships and 7 Laws
- `authority sources`:
  - `system-audit/THE-7-LAWS-OF-THE-7-OWNERSHIPS.md`
  - `The Ultimate Design/Capability Platform.txt`

## Core Identity

Skeleton is an ownership-governed composition platform.

It is not supposed to be a single flat operator console, a single subsystem-centered tool, or a whole-platform environment host. It is supposed to be a governed host that composes multiple ownership-aligned subsystem containers, each with the human-facing surfaces and embedded operating contexts appropriate to that owner.

The system exists to preserve semantic truth while still allowing rich human-facing work, platform-level observability, bounded operating contexts, reusable capability packages, bounded agents, external crossing, durable custody, and cross-owner handoff.

## Why It Exists

Skeleton exists because the platform needs a durable way to hold multiple different kinds of real things without letting any central layer quietly absorb their meaning.

The system needs:

- a thin host substrate
- true semantic owners
- human-operable subsystem containers
- workbench-heavy and admin-heavy surfaces
- bounded operating contexts where they are real
- durable custody without storage-driven ontology

## What It Owns

At the whole-platform level, Skeleton owns:

- the overall ownership-governed product shape
- the composition relationship between host shell, subsystem containers, surfaces, contexts, and environments
- the practical application of the 7 Ownerships / 7 Laws across the product

## What It Does Not Own

Skeleton as a whole does not justify:

- a global semantic blob layer
- a whole-platform environment ontology
- storage-first truth
- coordination sovereignty
- a flat page model that assumes all subsystems have the same human-facing shape

## Core Internal Structure Or Object Model

In principle, the system is made of:

- a thin Framework-owned host shell
- ownership-aligned subsystem containers
- typed operating surfaces inside those containers
- embedded operating contexts where local interaction rules matter
- true environments only where a bounded place has identity, rules, state, lifecycle, and readiness
- supporting runtime owners for Integration, Capability Platform, Agents, Execution Environment, Coordination, and Storage

## Human-Facing Structure In Principle

The human-facing structure should be:

- host shell
- subsystem container
- operating surface
- embedded operating context
- embedded environment, only when real

Different subsystems may legitimately have different human-facing shapes.

## Boundaries And Relationships

- `Framework` owns substrate, not semantic meaning.
- `Integration` owns external crossing, not the meaning of crossed-for things.
- `Capability Platform` owns capability package meaning.
- `Agents` owns bounded digital operators.
- `Execution Environment` owns bounded operating places.
- `Coordination` owns handoff and routing, not domain truth.
- `Storage` owns durable custody, not interpretation.

## Non-Negotiable Laws

- Ownership is determined by meaning, not proximity.
- Crossing does not imply ownership.
- The center must stay pure.
- Extension is preferred over centralization.
- Owners define meaning; other layers project, transport, persist, request, or consume.
- Boundaries outrank convenience.
- New inventory must not require rebuilding the factory.
- The platform is not a whole-app environment host unless the whole system truly becomes one bounded place, which current law and subsystem design do not justify.

## Common Deformation Risks

- recentering the product on one flat shell taxonomy
- mistaking rich UX for environment-scale architecture
- letting coordination become a hidden sovereign layer
- letting storage folders or schemas redefine ontology
- letting host-shell convenience logic absorb domain meaning
